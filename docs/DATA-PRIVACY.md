# 자산 데이터를 어디에 어떻게 저장할 것인가

## 1. 현재 상태

| | 저장 위치 | 누가 볼 수 있나 |
|---|---|---|
| 프로토타입 | 브라우저 localStorage | 그 브라우저를 쓰는 사람만 |
| `MULTIUSER.md` 초안 | Cloudflare D1 | Cloudflare + 내 CF 계정에 접근 가능한 사람 |

**초안 그대로 가면 보관 주체가 "나"에서 "Cloudflare"로 바뀐다.** 이 문서는 그 결정을 다시 본다.

---

## 2. 법적 위치 — 정확히 하자

한국 개인정보보호법에서 **"민감정보"는 법으로 열거된 목록**이다 (법 제23조, 시행령 제18조):
사상·신념, 노동조합·정당 가입, 정치적 견해, 건강, 성생활, 유전정보, 범죄경력, 생체인식정보,
인종·민족.

**자산정보는 이 목록에 없다.** 즉 법적 의미의 "민감정보"가 아니라 일반 **개인정보**다.
민감정보에 붙는 별도 동의 의무(제23조)는 적용되지 않는다.

그렇다고 보호 수준을 낮출 이유는 없다. 실질적으로는:

- **가족 전체의 순자산·계좌·부동산 주소가 한곳에 모인 데이터**다. 유출 시 피해는 표적 범죄
  (보이스피싱·침입절도)로 직결되며, 법적 분류보다 피해 양상이 중요하다.
- **용도에 따라 법적 지위가 달라진다.**
  - 내 가족만 쓴다 → 사적 이용. 개인정보처리자 의무 대부분이 적용되지 않는다.
  - **다른 가족에게도 열어준다 → 서비스가 된다.** 개인정보처리자가 되고,
    수집·이용 동의, 파기, 안전성 확보조치, 그리고 **국외이전(법 제28조의8)** 규정이 붙는다.
    Cloudflare에 저장하면 국외이전에 해당한다.

> 지금 "가족용"으로 시작해도, 지인에게 계정을 하나 열어주는 순간 성격이 바뀐다.
> 아래 설계는 그 전환이 와도 구조를 다시 갈아엎지 않아도 되게 하는 것이 목표다.

## 3. D1에 두면 실제로 어떻게 보관되나 (사실관계)

- **저장 시 암호화**: AES-256-GCM. 자동 적용이며 끌 수 없다.
- **전송 중 암호화**: Worker ↔ D1 구간 TLS.
- **키 관리 주체**: **Cloudflare**. 고객 관리 키(CMK)를 넣을 수 없다.
- **위치**: 생성 시 `--location apac`(아시아·태평양) 힌트를 줄 수 있으나
  **"가장 가까운 위치"일 뿐 보장되지 않는다.**
- **관할 강제(jurisdiction)**: EU와 FedRAMP만 지원한다. **한국·APAC을 법적으로 강제할 수단은 없다.**

여기서 중요한 결론:

> **"저장 시 암호화"는 디스크를 물리적으로 훔쳐가는 경우를 막아준다.
> 서비스 제공자 본인, 그리고 내 Cloudflare 계정을 탈취한 사람으로부터는 막아주지 않는다.**
> 키를 Cloudflare가 쥐고 있기 때문이다.

## 4. 핵심 — 서버가 하는 두 가지 일은 민감도가 완전히 다르다

| 서버의 역할 | 개인정보가 필요한가 | 이 일로 얻는 것 |
|---|---|---|
| **시세·실거래가 중계** | **전혀 필요 없다.** "삼성전자 종가 알려줘"가 전부 | P0-4 인증키 유출 해결, P1-5 속도, 캐시 공유 |
| **자산 데이터 보관** | 전부가 개인정보 | 다기기 동기화, 백업 |

앞선 분석에서 서버 도입의 이득으로 꼽은 것(**P0-4, P1-5, P1-5b**)은 **전부 첫 번째 역할에서 나온다.**
자산 데이터를 서버가 *읽을 수 있어야* 생기는 이득은 사실상 없다.

그리고 결정적으로 — **`core/`의 계산 함수는 이미 전부 순수 함수로 브라우저에서 돈다.**
서버가 자산 데이터를 집계할 필요가 애초에 없다.

→ **두 역할을 분리하면, 자산 데이터를 서버가 못 읽게 만들어도 잃는 것이 거의 없다.**

## 5. 선택지

### A. D1 평문 저장 (초안)
```
브라우저 ──평문──> Worker ──평문──> D1 (CF 키로 암호화)
```
- ✅ 가장 단순. 서버 집계·검색·구성원별 권한 제어 자유로움
- ❌ Cloudflare가 원리상 열람 가능
- ❌ 내 CF 계정이 털리면 전 가족 자산이 그대로 노출
- ❌ 서비스로 전환 시 국외이전 고지·동의 대상이 명확히 됨

### B. 필드 단위 암호화
자산명·계좌·주소·메모만 암호화하고 금액·분류·날짜는 평문으로 둔다.
- ✅ 서버 집계 일부 유지
- ❌ **금액과 분류만으로도 이미 충분히 민감하다** (총자산, 부동산 보유 여부)
- 절충안이지만 보호 효과가 어중간하다

### C. 로컬 우선 + 종단간 암호화 동기화 ← **권장**
```
브라우저 (IndexedDB 원본) ──암호문──> Worker ──암호문──> D1
   ↑ 여기서만 복호화                     서버는 내용을 모른다
```
- 자산 데이터는 브라우저에서 암호화된 뒤에만 서버로 나간다
- 서버(D1)에는 가구당 암호문 blob 하나만 쌓인다
- Worker는 **시세 중계 + 암호문 보관**만 한다
- ✅ Cloudflare가 봐도, 내 CF 계정이 털려도 내용을 알 수 없다
- ✅ 서버 집계가 필요 없으므로 **잃는 기능이 사실상 없다** (§4)
- ✅ 국외이전 논란에서 실질적으로 자유롭다 (평문 개인정보가 국외로 나가지 않는다)
- ❌ **구성원별 열람 권한 분리가 어렵다** (키를 가진 사람은 전부 본다)
- ❌ **잠금 암호를 잃으면 복구 불가** — 백업 문구/JSON 백업이 필수

## 6. ⚠️ Access 선택과 충돌하는 지점

앞서 인증을 **Cloudflare Access**로 정했다. E2EE와 결합할 때 문제가 하나 생긴다:

> **Access는 Google 로그인이라 "사용자가 기억하는 비밀"이 없다.
> 그런데 종단간 암호화는 키를 파생할 비밀이 필요하다.**

Google 계정으로 로그인만 하면 브라우저에는 암호화 키를 만들 재료가 없다.
Access 토큰으로 키를 만들면 Cloudflare가 키를 만들 수 있다는 뜻이라 E2EE가 성립하지 않는다.

**해결: 인증과 암호를 2단으로 분리한다.**

| | 담당 | 주체 |
|---|---|---|
| **Access 로그인** | *누가 들어오는가* | Cloudflare (Google/이메일 OTP) |
| **데이터 잠금 암호** | *데이터를 열 수 있는가* | 사용자만 (서버로 전송되지 않음) |

```js
// 잠금 암호 → 암호화 키. 전부 브라우저에서 일어난다.
const keyMaterial = await crypto.subtle.importKey(
  "raw", enc.encode(passphrase), "PBKDF2", false, ["deriveKey"]);
const key = await crypto.subtle.deriveKey(
  { name: "PBKDF2", hash: "SHA-256", salt: householdSalt, iterations: 600_000 },
  keyMaterial, { name: "AES-GCM", length: 256 }, false, ["encrypt", "decrypt"]);
```

**여기서 뜻밖의 이점**: 이 PBKDF2는 **브라우저에서** 돈다. 앞서 측정한
Workers 무료 플랜 CPU 10ms 제약과 **무관하다.** 600,000회(OWASP 권장)를 마음껏 쓸 수 있다.
서버에서 하면 272ms로 27배 초과였던 그 연산이, 클라이언트에서는 공짜다.

가족이 공유하는 잠금 암호 1개로 시작하고, 나중에 구성원별 키가 필요해지면
가구 키를 각자 공개키로 감싸는 방식으로 확장한다.

## 7. 어떤 방식을 택하든 지킬 것

- **계좌번호는 뒤 4자리만** 저장한다 (프로토타입이 이미 그렇게 한다 — 유지).
- **소유자는 실명 대신 별칭** ("본인/배우자/자녀/공동").
- **주민등록번호 필드를 만들지 않는다.** 지금 없다. 앞으로도 넣지 않는다.
  (고유식별정보는 별도 규제 대상이고, 이 앱에 필요 없다.)
- **JSON 백업에서 인증키를 제외한다.** 현재 `DB.set.rtmsKey`가 백업 파일에 평문으로 들어간다.
  서버 중계로 옮기면 애초에 클라이언트에 키가 없어진다 (P0-4).
- **백업 파일도 암호화 옵션을 준다.** 백업은 사용자 디스크·클라우드 드라이브로 흘러간다.
- **`workers.dev` 대신 커스텀 도메인**을 쓴다. `*.workers.dev`는 공용 접미사라
  쿠키 격리·피싱 측면에서 자체 도메인이 낫다.
- **XSS를 먼저 잡는다.** E2EE를 해도 브라우저에서 복호화하므로,
  XSS가 있으면 평문을 그대로 빼갈 수 있다. **암호화는 XSS를 대신하지 못한다.**
  (`ANALYSIS.md` P2-7 → P0 승격 항목)

## 8. 권장 결론

**C안 (로컬 우선 + E2EE 동기화)** 을 권한다. 근거:

1. 서버 도입의 실익(P0-4·P1-5·P1-5b)은 **시세 중계에서만** 나오고, 그 역할은 개인정보를
   전혀 다루지 않는다.
2. `core/` 계산이 이미 브라우저에서 도는 순수 함수라 **서버 집계가 필요 없다.**
   E2EE의 최대 단점이 이 앱에는 해당하지 않는다.
3. 가족 자산 데이터의 보관 책임을 제3자에게 넘기지 않는다.
4. 나중에 다른 가족에게 열어줘도 국외이전 쟁점이 실질적으로 생기지 않는다.

**포기하는 것**은 구성원별 서버측 열람 권한 분리 하나다. 가족 단위에서는
"부부는 전체 공유, 자녀 계정은 별도 가구" 정도로 우회할 수 있다.

### 수정된 구조

```
브라우저
  ├── IndexedDB          자산 원본 (평문, 이 기기 안에서만)
  ├── core/              평가·집계 (순수 함수, 서버 불필요)
  └── AES-GCM 암·복호화   잠금 암호에서 파생한 키
        │
        │  암호문 blob만
        ▼
  Cloudflare Worker  ── Access로 인증
        ├── /api/sync     암호문 blob 보관·동기화        → D1
        ├── /api/quote    시세 중계 (개인정보 없음)      → Cache API
        └── /api/rtms     실거래가 중계 (키는 서버 secret) → D1/KV 월별 캐시
```

이 구조에서 D1에 실제로 들어가는 것은 **① 가구별 암호문 blob**과
**② 종목 시세·실거래가 캐시(개인정보 아님)** 뿐이다.
