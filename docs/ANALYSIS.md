# 가족 통합 자산관리 시스템 — 프로토타입 문제점 분석

- 대상: `prototype/index.html` (단일 파일 HTML, 2,170줄 / 114KB)
- 분석일: 2026-09-02
- 요약: **동작하는 데모로서는 완성도가 높으나, 자산 "관리" 도구로 쓰기에는 금액 계산 로직에
  신뢰할 수 없는 부분이 있고, 데이터가 조용히 사라질 수 있으며, 인증키가 제3자 서버로 새어나간다.**

분류 기준
- **P0 — 치명적**: 잘못된 숫자를 사실처럼 보여주거나, 데이터/비밀정보가 유실·유출됨
- **P1 — 중대**: 실사용 시 곧바로 부딪히는 기능/성능 결함
- **P2 — 구조**: 지금 당장은 안 아프지만 개선을 계속하려면 반드시 풀어야 하는 부채
- **P3 — 품질**: UX·접근성·표현

## P0. 치명적 — 숫자를 믿을 수 없음

### P0-1. 예금·적금 이자가 만기를 무시하고 무한히 증가한다
`accrued()`는 `end`(만기일)를 **파라미터로 받지도 않는다**. 가입일부터 "오늘"까지 단리를
무조건 누적한다.

```js
function accrued(principal, ratePct, startISO, refDate){
  if(!startISO || principal<=0 || ratePct<=0) return 0;
  const s = dOf(startISO), r = refDate || new Date();
  const days = Math.max(0, Math.round((r - s)/86400000));
  return principal * (ratePct/100) * days / 365;   // ← end 없음
}
```

실제 계산 결과 (샘플 데이터 기준, 2026-09-02):

| 자산 | 원금 | 만기 | 화면 표시 평가액 |
|---|---:|---|---:|
| 하나 정기예금 12M (3.45%) | 80,000,000 | 2026-09-01 (만기 경과) | **82,767,562** |
| 위 자산을 5년간 방치하면 | 80,000,000 | — | **96,575,123** |
| 주택청약종합저축 (2.8%, 2018년 가입) | 17,800,000 | 없음 | **22,037,083** |

만기가 지난 예금이 계속 불어나고, 8년짜리 청약저축은 실제 납입액과 무관하게 424만원의
가공 이자가 붙는다. 총자산·순자산·수익률에 그대로 반영된다.

추가로:
- **단리**다. 정기예금은 보통 만기 일시 복리/단리이지만, 청약저축·적금은 계산 방식이 전혀 다르다.
- **세전**이다. 이자소득세 15.4%가 반영되지 않는다.
- **적금(월납)에 원금 전액이 처음부터 들어있다고 가정**한다. `DEFMODE`에서 `적금:"RATE"`인데,
  월 100만원씩 12개월 넣는 적금의 실제 이자는 이 계산의 약 절반이다.

### P0-2. "투자원금 추이" 그래프가 계산 자체를 안 한다
`reconstruct()`의 원금 시계열:

```js
vals.forEach((v,i)=> { if(v) principal[i] += curPrin; });
```

`curPrin`은 **오늘 시점의 원금**이다. 이걸 과거 모든 시점에 그대로 더한다. 즉 3년 전에도
오늘과 같은 원금을 투입했던 것처럼 그려진다. 자산 추이 탭의 회색 "투자원금" 선은
**시계열이 아니라 상수선**이며, 여기서 파생되는 "기간 수익" 해석이 전부 틀린다.

올바르게 하려면 `qtyAt()`처럼 거래기록을 누적해 시점별 투입원금을 만들어야 한다.

### P0-3. AUTO가 아닌 자산은 과거 값이 "오늘 값"으로 채워진다
같은 `reconstruct()`에서 MANUAL 자산(펀드·연금·IRP·보험·실물·부채)은 조건 분기 끝에서
`return curVal` — 즉 **3년 전 값 = 오늘 값**.

샘플 기준 MANUAL/QUOTE 자산 합계는 총자산의 상당 부분이다. 결과적으로 "3년 자산 추이"는
과거가 실제보다 크게 부풀려진 채 거의 평평하게 그려지고, 실제 증가분은 축소돼 보인다.
사용자가 이 그래프를 보고 "우리집 자산이 3년째 제자리"라고 오판할 수 있다.

### P0-4. 공공데이터포털 인증키가 제3자 프록시로 전송된다
`rtmsTrades()`는 인증키를 **URL 쿼리에 넣고** `netFetch()`에 넘긴다. `netFetch()`는 직접 호출이
실패하면 자동으로 외부 프록시로 넘어간다.

```js
const DEFAULT_PROXIES = [
  "https://api.allorigins.win/raw?url=",
  "https://corsproxy.io/?url=",
  "https://api.codetabs.com/v1/proxy?quest="];
```

브라우저에서 data.go.kr 직접 호출은 CORS로 거의 항상 막히므로, **정상 경로가 곧 프록시 경로**다.
인증키 전문이 운영 주체를 알 수 없는 세 개의 서버 접근 로그에 남는다. 설정 탭에 경고 문구는
있지만 **기본값이 프록시 사용**이라 사실상 opt-out 설계다.

같은 키가 `DB.set.rtmsKey`로 localStorage에 평문 저장되고, **JSON 백업 파일에도 그대로 포함**되어
내보내진다.

### P0-5. localStorage 용량 초과 시 데이터가 조용히 사라진다
저장소가 단일 키 하나에 자산·거래·**일별 시세 이력 전체**를 담는다.

```js
save(){
  const s = JSON.stringify(DB);
  try{ localStorage.setItem(SKEY, s); ... }
  catch(e){ this.mem = JSON.parse(s); this.mode = "메모리 전용(...)"; }   // ← 여기
}
```

- 종목 20개 × 3년 일봉(약 750일) = 15,000 포인트. `[일별시세 일괄 수신]` 한 번이면 수백 KB~MB.
- 5MB 한도를 넘으면 `setItem`이 throw → 조용히 메모리 모드로 전환.
- `Store.load()`는 **`getItem`이 throw할 때만** 메모리 모드를 감지한다. quota 초과는 `setItem`에서
  나므로, 다음 새로고침 때는 정상 모드로 판단하고 **넘치기 직전의 낡은 스냅샷을 읽어온다.**
  그 사이 입력분은 전부 소실되고, 상태바 문구 말고는 사용자에게 알리는 장치가 없다.

### P0-6. 보유수량 역산이 과거 이력을 임의로 재조정한다
```js
const adj = (total && Math.abs(total-nowQ)/Math.max(nowQ,1) > 0.01) ? nowQ/total : 1;
return cum * adj;
```
거래기록 합계(`total`)와 현재 수량(`a.qty`)이 1% 넘게 어긋나면 **과거 수량 전체에 배수를 곱한다.**
거래를 일부만 입력한 사용자(대부분의 실제 사용자)에게는 근거 없는 숫자가 나온다.
`total`이 음수면 과거 수량이 음수가 된다. 경고도, 표시도 없다.

## P1. 중대 — 실사용에서 곧바로 부딪힘

### P1-1. LTV 계산이 관계없는 항목을 섞는다
```js
ltv: re ? debt/re*100 : 0    // debt = 전체 부채, re = 전체 부동산
```
신용대출·마이너스통장·임대보증금이 분자에 들어가고, 전세보증금(자산)·임대 오피스텔이 분모에
들어간다. 샘플 기준 표시값 **21.0%** vs 실제 자택 주담대 LTV **27.0%**. 자산-부채를 연결하는
필드가 아예 없는 것이 근본 원인이다.

### P1-2. 부동산 "연결대출"이 소유자 기준이라 이중계산된다
```js
const loan = ROWS.filter(x => x.debt && x.cat === "주택담보대출" && x.owner === r.owner)
```
같은 소유자가 부동산을 2건 가지면 **두 행 모두에 같은 대출 전액이 표시**되고, "순자산" 열이
합계에서 이중으로 차감된 것처럼 보인다. 자산에 `linkedDebtId` 같은 연결 필드가 필요하다.

### P1-3. 원금 0인 자산의 수익률이 무한대로 부풀려진다
`evaluate()`에서 `principal`이 없고 `value`만 입력된 자산(현금성 등)은 원금 0 → 손익 = 평가액 전액.
개별 행에서 `fmtPct(0)`로 가드되지만 **총계 `TOT.pl`에는 평가액 전액이 "수익"으로 합산**된다.

### P1-4. 통화가 한 행 안에서 섞여 표시된다
USD 자산의 `평균단가`·`현재가` 열은 달러, `원금`·`평가액` 열은 원화 환산이다. 열 머리글에 통화
표기가 없어 Apple 행이 `195 / 210 / 2,925,000 / 3,150,000` 처럼 보인다.
또한 환율은 **오늘 환율을 취득원가에도 적용**한다 (`principal = rawP * fxr`). 취득 시점 환율이
아니므로 환차손익이 평가손익에 뒤섞인다.

### P1-5. 시세 조회에 타임아웃·동시성·캐시가 전부 없다
```js
for(const p of routes){ ... const res = await fetch(u, ...); }   // 순차
```
- `AbortController` 없음 → 프록시가 응답하지 않으면 브라우저 기본 타임아웃까지 대기.
- `refreshQuotes()`는 종목을 **순차** 조회. 20종목 × (직접 실패 + 프록시 3개 시도) = 최대 80회 왕복.
- `estimateProperty()`는 개월 수만큼 순차 호출(6개월 = 6회). 각 500건.
- 결과 캐시 없음 → 탭 이동/재조회 때마다 다시 전부 호출.

### P1-6. 비공식 API 의존
- `api.finance.naver.com/service/itemSummary.nhn` — 네이버 비공개 엔드포인트. 예고 없이 사라진다.
- `query1.finance.yahoo.com/v8/finance/chart` — 비공식이며 이용약관상 재배포 제한이 있다.

둘 다 죽으면 자동 시세 기능 전체가 정지한다. 대체 경로나 명시적 폴백 UI가 없다.

### P1-7. 실거래가 추정이 통계적으로 취약하다
```js
const avgUnit = matched.reduce((s,r)=> s+r.unit, 0)/matched.length;
const value = area ? avgUnit*10000*area : ...
```
- **단순 평균**이라 특이거래(직거래·증여성 저가거래) 1건에 크게 흔들린다. 중위값/이상치 제거 없음.
- 층·향·동·리모델링 여부를 무시한다. 저층 급매와 로열층이 동일 가중.
- 기간 가중이 없다. 6개월 전 거래와 지난주 거래가 같은 비중.
- `numOfRows=500` 고정, **페이지네이션 없음** → 강남구처럼 거래가 많은 지역은 누락된다.

### P1-8. 시세 이력 키가 자산 생명주기와 어긋난다
`priceKey()`가 종목코드 기준(`KR:005930`)이라 여러 계좌에 나눠 담은 동일 종목이 이력을 공유한다.
- 자산 하나를 삭제해도 `delAsset()`은 `DB.hist["RE:"+id]`만 지운다 → 주식 이력은 **영구히 남는다**.
- 종목코드를 수정하면 이전 키의 이력이 **고아 데이터로 남아 계속 누적**된다 (P0-5의 용량 압박에 기여).

### P1-9. 매 셀 편집마다 화면 전체를 다시 그린다
`beginEdit()`의 `commit()`이 `renderAll()`을 호출한다. `renderAll()`은 대시보드 도넛·막대·누적막대,
자산표, 카테고리 2개 표, 주식표+트리맵, 부동산표+차트를 **전부 재생성**한다.
셀 하나 고칠 때마다 SVG 수백 개가 다시 만들어지고, Tab 연속 편집이 20ms `setTimeout`으로
새 DOM을 다시 찾는 구조라 자산이 수백 건이면 눈에 띄게 끊긴다.

### P1-10. 오류를 사용자에게 제대로 알리지 않는다
```js
status("시세 갱신 완료 ... " + (errs.length ? " · 경고 " + errs.length + "건: " + errs[0] : ""));
```
실패한 종목 목록을 볼 방법이 없다. `errs[0]` 하나만 상태바에 스쳐 지나간다.
어떤 종목이 최근 저장 시세로 대체됐는지 표에서 구분되지 않아, **며칠 전 가격을 현재가로 오인**한다.

## P2. 구조 — 개선을 계속하려면 먼저 풀어야 함

### P2-1. 단일 파일 2,170줄, 테스트 0개
- 전역 스코프에 함수 100개 이상. `showTab`/`delTrade`는 인라인 `onclick` 때문에 전역이어야만 한다.
- 모듈·번들·타입 없음.
- **금액 계산 함수(`evaluate`, `accrued`, `qtyAt`, `reconstruct`, `totals`)에 단위 테스트가 하나도 없다.**
  P0-1~P0-3 같은 버그가 잡히지 않고 남은 직접적인 이유다.

권장 분리: `core/`(평가·집계, 순수 함수 + 테스트) / `data/`(저장소·스키마·마이그레이션) /
`net/`(시세 어댑터) / `ui/`(렌더링). 계산 계층만 먼저 떼어내고 테스트를 붙이는 것이
비용 대비 효과가 가장 크다.

### P2-2. 스키마 버전·마이그레이션이 없다
`DB = {v:1, ...}`로 버전 필드는 있으나 **읽는 곳이 없다**. `boot()`은 `Object.assign`으로 병합만 한다.
필드를 하나라도 바꾸면 기존 사용자 데이터가 깨지고, 되돌릴 수단이 없다.

### P2-3. 가져오기 검증이 사실상 없다
```js
if(!d || !Array.isArray(d.assets)) throw new Error("형식이 올바르지 않습니다");
DB = Object.assign({...}, d);
DB.seq = Math.max(DB.seq||1, ...DB.assets.map(a=>a.id||0), ...) + 1;
```
- 자산 필드 타입 검증 없음. 문자열이 들어와도 그대로 계산에 들어간다.
- `Math.max(...배열)` 스프레드 — 항목이 수만 건이면 스택 오버플로.
- 가져오기 전 **현재 데이터 자동 백업이 없다.** 잘못된 파일을 넣으면 즉시 되돌릴 수 없다.

### P2-4. `nextId()`를 자산과 거래가 공유한다
`DB.seq++` 하나를 자산·거래가 같이 쓴다. 동작은 하지만 ID 의미가 흐려지고, 병합/동기화 기능을
넣는 순간 충돌한다.

### P2-5. 통화가 KRW/USD 하드코딩
`(a.cur||"KRW").toUpperCase()==="USD" ? rate : 1` — 엔화·유로 자산을 넣을 수 없다.
환율도 단일 값(`ST.fx`) 하나만 보관한다.

### P2-6. 거래기록이 자산 단위에 묶여 있다
같은 종목을 두 계좌로 나눠 보유하면 거래를 어느 자산에 넣을지 정할 수 없고, `qtyAt()`은
자산별로만 계산한다. 계좌 이동·대체출고 같은 실제 케이스를 표현할 수 없다.

### P2-7. `esc()`가 작은따옴표를 이스케이프하지 않는다
```js
.replace(/[&<>"]/g, ...)   // ' 없음
```
현재 코드에서는 `esc()` 결과가 큰따옴표 속성에만 들어가서 실제 취약점은 되지 않는다. 다만
`class='...'` 처럼 작은따옴표 속성을 쓰는 곳이 이미 섞여 있어, 앞으로 한 줄만 잘못 추가해도
자산명·메모를 통한 HTML 주입이 성립한다. 지금 고쳐 두는 편이 싸다.

## P3. 품질 — UX·접근성·표현

- **스티키 헤더 겹침**: `nav.tabs{top:52px}`가 하드코딩. 헤더가 `flex-wrap`으로 줄바꿈되면
  (좁은 화면) 탭이 헤더 아래로 파고든다.
- **키보드로 표를 편집할 수 없다**: 인라인 편집 진입이 `dblclick` 전용. Enter 진입 경로가 없다.
- **접근성 전무**: `aria-*` 없음, 탭 UI에 `role="tablist"` 없음, 표에 캡션/스코프 없음,
  포커스 표시가 기본값, 손익을 **색상만으로** 구분(색각 이상 사용자는 구분 불가).
- **모바일**: `font-size:13px` 고정 + `white-space:nowrap` 16열 표. 사실상 데스크톱 전용.
- **다크모드 없음**.
- **인라인 `onclick` 사용** → CSP(`script-src 'self'`) 적용 불가.
- **단위 표기 불일치**: 카드에는 `fmtWon`(억 단위 2자리 반올림), 표 합계에는 `fmtNum`(원 단위).
  같은 값이 "9.2억"과 "920,000,000"으로 따로 보여 검산이 어렵다.
- **한국식 금액 입력 미지원**: `pnum()`이 콤마·`원`·`%`만 제거. "1.2억", "3,000만"은 0이 된다.
- **첫 실행에 `confirm()` 팝업**으로 샘플 데이터를 묻는다. 실수로 확인하면 샘플이 실데이터처럼 섞이고,
  샘플임을 표시하는 플래그가 없어 이후 구분이 불가능하다.
- **CSV 내보내기가 화면 필터 결과만** 담는다. "백업"으로 오해하기 쉽다.
  또 `&amp;`만 되돌리고 `&lt;`·`&gt;`·`&quot;`는 이스케이프된 채로 나간다.
- **스냅샷 관리 부재**: 하루에 여러 번 눌러도 중복 방지가 없고, 개별 삭제 없이 "전체 초기화"뿐.
- **시세 기준일 미표시**: 새로고침 후 `boot()`가 마지막 저장 시세를 현재가로 복원하는데,
  그것이 며칠 전 값이라는 표시가 어디에도 없다.
- **과거 시세 기록의 비일관**: `reHistAdd()`는 `d >= todayISO()`일 때만 `a.value`를 갱신한다.
  과거 날짜로 기록하면 이력과 평가액이 어긋난 채 남는다.
- **`URL.createObjectURL` 미해제** (`exportJson`/`exportCsv`) — 경미한 메모리 누수.
- **누적영역 차트가 음수 시리즈를 버린다**: `series.filter(s => s.vals.some(v=>v>0))`.
  부채를 음수로 넣는 대시보드 방식과 일관되지 않는다.
- **도넛 차트가 카테고리 11개 초과분을 조용히 버린다** (`slice(0,11)`). "기타"로 묶지 않는데
  중앙에는 총자산 전액이 표시되어 합이 맞지 않는다.
